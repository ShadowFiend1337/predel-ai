# Диаграммы взаимодействия

## Реализация: синхронная отправка

Целевые условия текстового сценария, пользовательские действия и обработка потери ответа описаны в [UC-01](../docs/03_use_case_text_submission.md). Диаграмма ниже сохраняет пометку реализации; наличие связи с UC не означает выполнения всех его требований.

```mermaid
sequenceDiagram
    actor Student as Ученик
    participant API as API PredelAI
    participant Extract as Извлечение записи
    participant Legacy as Прежний оценщик
    participant Parser as Разбор шагов
    participant A as Оценщик A
    participant B as Оценщик B
    participant R as Арбитр
    participant DB as База данных

    Student->>API: task_id и текст / файлы
    API->>API: Аутентификация, проверка запроса, загрузка задачи
    loop Для каждого файла, если они переданы
        API->>API: Проверить текущий файл: размер, содержимое, формат
        alt Изображение
            API->>Extract: Подготовленное изображение
            Extract-->>API: Запись и OCR-сигналы
        else PDF или текстовый файл
            API->>Extract: Исходный файл
            Extract-->>API: Текстовый слой / декодированный текст
        end
    end
    API->>API: Объединить извлечённую запись или подготовить введённый текст
    alt Только итоговый ответ
        API->>API: Предметный отказ без проверки ИИ
    else Задание вне №13–15
        API->>Legacy: Прежняя проверка решения
        Legacy-->>API: Ответ с текстовыми маркерами
    else Специализированная проверка
        API->>Parser: Условие и запись
        alt Разбор пригоден
            Parser-->>API: Структурированные шаги, в том числе допустимое резервное восстановление
        else Разбор не дал пригодного результата
            Parser-->>API: Ошибка, оценивание без шагов
        end
        API->>API: Предметные программные проверки по применимости
        par При параллельной конфигурации
            API->>A: Общий контекст
            A->>A: Вызов модели, валидация, пересчёт, внутренняя калибровка
            A-->>API: Оценка A или ошибка
        and
            API->>B: Общий контекст
            B->>B: Вызов модели, валидация, пересчёт, внутренняя калибровка
            B-->>API: Оценка B или ошибка
        end
        alt Арбитр требуется по таблице реализации
            API->>R: Контекст и результаты A/B
            R->>R: Валидация, пересчёт, внутренняя калибровка
            R-->>API: Оценка или ошибка
            API->>API: Защита общего результата / принятие / резервная ветка
        else Арбитр не требуется или оценщик недоступен
            API->>API: Согласованный результат или ветка отказа A/B
        end
        API->>API: Итоговая калибровка №13/15
        API->>API: Учёт существенной OCR-неопределённости
    end
    API->>API: Формирование пояснений и полей результата
    API->>DB: Сохранить попытку и JSON этапов
    alt Транзакция зафиксирована
        DB-->>API: Идентификатор попытки
        API-->>Student: HTTP 200, AttemptOut
    else Сохранение не выполнено
        DB-->>API: Ошибка
        API-->>Student: Ошибка запроса
    end
```

Извлечение пустого текста или неверный запрос останавливают последовательность до оценивания; HTTP-коды приведены в C-01. Ветка технической ошибки внутри оценивания может сформировать сохраняемый результат текущего API; целевые требования к отсутствующей оценке описаны отдельно. Обновление статистики пользователя опущено как второстепенное для кейса действие после сохранения попытки.

## Целевая интеграция: надёжный приём и polling

```mermaid
sequenceDiagram
    participant LMS as LMS школы
    participant API as API проверок
    participant DB as Хранилище заданий
    participant D as Диспетчер событий
    participant Q as Очередь
    participant W as Обработчик
    actor C as Куратор

    LMS->>API: POST /checks, Idempotency-Key
    API->>DB: Проверить ключ и хеш запроса в пределах клиента
    alt Новый ключ
        API->>DB: Транзакция: CheckJob и OutboxEvent
        DB-->>API: Транзакция зафиксирована
        API-->>LMS: 202, check_id, Location
        D->>DB: Прочитать недоставленные события
        D->>Q: Доставить событие с повторами при ошибке
        Q->>W: Обработать check_id
        W->>DB: Проверить состояние, зафиксировать processing
        W->>W: Выполнить проверку по целевым правилам
        alt Окончательная автоматическая оценка
            W->>DB: Сохранить результат и completed
        else Требуется куратор
            W->>DB: Транзакция: предварительный результат, CuratorReview, needs_curator_review
            C->>API: Назначить проверку на себя с ожидаемой версией
            API->>DB: under_review и assigned_to
            C->>API: Подтвердить / изменить, версия и причина
            API->>DB: Транзакция: ручное решение, reviewed, история
        else Техническая неудача без оценки
            W->>DB: failed, безопасная ошибка, result=null
        end
    else Эквивалентный повтор
        DB-->>API: Существующая проверка
        API-->>LMS: Тот же check_id, текущее состояние
    else Ключ использован с другим запросом
        API-->>LMS: 409
    end
    LMS->>API: GET /checks/{check_id}
    API->>DB: Проверить владельца и прочитать состояние
    DB-->>API: Состояние и доступный результат
    API-->>LMS: 200, CheckResult
```

При неуспешном сохранении API не подтверждает приём. Временная недоступность очереди после фиксации транзакции не теряет запрос: событие остаётся в хранилище. Повторная доставка не создаёт второй итоговый результат; переходы проверяют версию и текущее состояние.

## Дополнительный webhook — отдельный вариант

```mermaid
sequenceDiagram
    participant Delivery as Сервис уведомлений
    participant LMS as LMS школы
    Delivery->>LMS: Подписанное уведомление, event_id, check_id, версия результата
    LMS->>LMS: Проверить подпись и повтор event_id
    LMS-->>Delivery: Подтверждение приёма
```

Webhook не входит в первую целевую версию. Перед включением согласуются алгоритм подписи, ответ подтверждения, число повторов, интервалы и срок доставки. Polling остаётся способом получения текущего результата; GET всегда инициирует LMS.

# Инструменты проверки аналитического кейса

Эта папка помогает воспроизвести контракт и проверки. Она не является частью приложения `predel`, не вызывает реальные модели и не обращается к рабочей базе данных.

| Файл | Назначение |
|---|---|
| [build_api_package.py](build_api_package.py) | Собирает две OpenAPI-спецификации и две коллекции Postman |
| [target_contract_models.py](target_contract_models.py) | Проверяемые модели проектируемого API 2.0 и правил согласованности полей |
| [uc01_stand.py](uc01_stand.py) | Учебный HTTP-стенд с настоящими обработчиками, JWT и ограничителем; оценивание и хранение заменены |
| [verify_api_package.py](verify_api_package.py) | Проверяет файлы и примеры; превращает отчёт Newman в протокол без токенов |
| [verify_sql.mjs](verify_sql.mjs) | Выполняет семь SQL-запросов на синтетических данных в PGlite и проверяет граничные случаи |
| [prepare_sql_dataset.py](prepare_sql_dataset.py) | Подготавливает исходную CSV, фиксирует ошибки типов и контрольную сумму; рабочие строки сохраняет вне проекта |
| [analyze_sql_dataset.mjs](analyze_sql_dataset.mjs) | Выполняет SQL на подготовленном реальном снимке; сохраняет в кейсе только агрегаты и протокол |
| [prepare_comparison_dataset.py](prepare_comparison_dataset.py) | Подготавливает вторую CSV с обеими системами; эталон — `true_score` команды |
| [analyze_comparison_dataset.mjs](analyze_comparison_dataset.mjs) | Проверяет связи и JOIN, сравнивает продукты, сохраняет агрегированный протокол |

Для чтения кейса запускать инструменты необязательно. Начать можно с [описания API](../docs/11_api_specification.md) и [готового протокола](../docs/12_api_verification_protocol.md).

## Подготовка окружения

Папки `predel` и `predelai-ai-checking-pipeline-case-compact` должны находиться рядом. Нужен Python с зависимостями `predel/backend`, а также Node.js и npm. Используйте отдельное учебное окружение Python, чтобы дополнительные библиотеки не меняли окружение приложения. Команды ниже выполняются из корня папки кейса; `python` должен указывать на это окружение.

Дополнительные библиотеки:

```sh
python -m pip install PyYAML==6.0.3 jsonschema==4.23.0 openapi-spec-validator==0.7.2
npm install --prefix /tmp/predel-api-node newman@6.2.1
```

Зависимости backend определены в соседнем проекте; существующее рабочее окружение можно использовать после проверки совместимости. Версии библиотек выполненного запуска записаны в отчёте.

## Сборка и проверка файлов

```sh
PYTHONDONTWRITEBYTECODE=1 python tools/build_api_package.py
PYTHONDONTWRITEBYTECODE=1 python tools/verify_api_package.py
```

Сборка перезаписывает только `contracts/openapi-current.yaml`, `contracts/openapi-target-v2.yaml` и две коллекции в `postman`. Ручные изменения этих файлов при пересборке потеряются: постоянные изменения нужно внести в генератор или целевые модели. Проверяющий скрипт обнаруживает расхождения сохранённых файлов с генератором.

Без отчёта Newman создаётся `verification/api-static-report.json`. Он подтверждает только проверки файлов и не заменяет протокол HTTP-запуска.

## Запуск HTTP-проверок

В первом терминале:

```sh
PYTHONDONTWRITEBYTECODE=1 python tools/uc01_stand.py --serve --port 8765
```

Во втором терминале:

```sh
/tmp/predel-api-node/node_modules/.bin/newman run postman/uc01-current.postman_collection.json --reporters cli,json --reporter-json-export /tmp/predel-newman-report.json
PYTHONDONTWRITEBYTECODE=1 python tools/verify_api_package.py --newman-report /tmp/predel-newman-report.json
```

Результат — [verification/uc01-api-report.json](../verification/uc01-api-report.json). При ошибке проверки успешный протокол не формируется. После окончания остановите стенд сочетанием Ctrl+C в первом терминале. Если порт занят, задайте другой через `--port` и передайте Newman `--env-var base_url=http://127.0.0.1:НОМЕР_ПОРТА`.

Полный отчёт Newman остаётся в `/tmp`: он содержит учебные JWT и окружение. В публикуемый отчёт переносятся только названия запросов, статусы, проверки, отдельные наблюдаемые поля и контрольные суммы. Реальные секреты для стенда не нужны. Стенд слушает только локальный адрес; его служебные маршруты предназначены для подготовки учебных данных.

## Работа через Postman

Можно импортировать текущую коллекцию в Postman и запустить её целиком по порядку. Первый запрос получает учебные токены; группы сбрасывают данные самостоятельно. Используйте отдельное окружение без переменных `token` и `other_token`, которые перекроют значения, полученные коллекцией. Укажите `base_url=http://127.0.0.1:8765`. Для машиночитаемого протокола используйте Newman по командам выше.

Целевая коллекция v2 требует будущей реализации, двух тестовых токенов и раздельной подготовки сценариев. Порядок описан в [протоколе](../docs/12_api_verification_protocol.md). Синтаксическая проверка этой коллекции не является запуском целевого API.

## Проверка SQL

Из корня кейса:

```sh
npm install --prefix /tmp/predel-sql-validation @electric-sql/pglite@0.5.8
node tools/verify_sql.mjs /tmp/predel-sql-validation
```

[PGlite](https://pglite.dev/docs/) выполняет PostgreSQL в памяти процесса без отдельного сервера. Проверяющий скрипт создаёт временную таблицу, загружает восемь синтетических работ, проверяет семь запросов и граничные случаи. Изменения тестовых строк откатываются после каждого сценария. Итог записывается в [SQL-протокол](../verification/sql-report.json) только после успешного выполнения всех проверок.

Назначение запросов и ручной запуск через PostgreSQL описаны в [SQL-блоке](../sql/README.md). Реальная Google-таблица этим скриптом не скачивается и не анализируется.

## Повторение анализа реальной выборки

Нужен исходный CSV, полученный из предоставленной таблицы. Скрипты не скачивают таблицу сами и не меняют её. Для воспроизведения опубликованных чисел SHA-256 CSV должен совпасть с [паспортом снимка](../docs/15_dataset_analysis.md); иной снимок может дать другой результат.

Из корня кейса, после установки PGlite по команде выше:

```sh
python tools/prepare_sql_dataset.py /путь/к/исходной-выгрузке.csv --output-dir /tmp/predel-real-sql
node tools/analyze_sql_dataset.mjs /tmp/predel-sql-validation /tmp/predel-real-sql
```

Для подготовительного скрипта достаточно Python 3.9+ со стандартной библиотекой. Он сохраняет в рабочем каталоге `prepared.json`, `manifest.json` и `import-issues.json`. Исходный CSV не изменяется. Неразбираемая дата становится `NULL` в подготовленной колонке, а исходное значение остаётся в `*_raw`. Повторные ID и отсутствие ключевых полей останавливают расчёт до уточнения гранулярности.

SQL выполняется в памяти процесса. Полные результаты, включая строки для предметного разбора, сохраняются в `detailed-sql-results.json` только в рабочем каталоге вне проекта. В [проектный протокол](../verification/dataset-analysis-report.json) попадают агрегаты, пары баллов без ученических ID, основания исключений и контрольные суммы. Баллы дополнительно пересчитываются независимо от SQL для проверки знаменателя, совпадений и абсолютной ошибки.

Сценарий рассчитан на формат этой предоставленной выборки. Он фиксирует модель как «Стобалльный репетитор» и эталон как `curator_points` по подтверждению автора кейса; для другого источника нужно изменить паспорт и правила, а не переиспользовать эти подписи молча. Сведения о временной зоне пока отсутствуют, поэтому результат запроса 07 помечен условным. При подтверждении зоны и смысла событий нужно обновить паспорт и трактовку показателя.

## Повторение сравнения двух продуктов

Этот отдельный сценарий рассчитан на вторую CSV, где `PredelAI_score` и `their_ai_score` находятся в одной строке. Эталон — `true_score` команды проекта; оценки куратора сохраняются отдельно. Скрипт рассчитан на подтверждённое назначение этого источника, поэтому его подписи нельзя переносить на произвольный набор.

```sh
python tools/prepare_comparison_dataset.py /путь/к/второй-выгрузке.csv --output-dir /tmp/predel-comparison-analysis
node tools/analyze_comparison_dataset.mjs /tmp/predel-sql-validation /tmp/predel-comparison-analysis/prepared-comparison.json
```

Python 3.9+ использует стандартную библиотеку; Node.js — уже установленную PGlite 0.5.8. Подготовленный JSON сохраняется вне проекта и содержит только служебные ключи, номера заданий и оценки. Изменение исходных данных требует нового паспорта: SHA-256 связывает каждый протокол с конкретным снимком.

[Модель связей](../sql/comparison/README.md) и [результаты](../docs/21_product_comparison.md) описывают четыре SQL-запроса. Семь встроенных синтетических сценариев проверяют пропуски, ноль, эталон, ключи и пустую выборку. Расчёт создаёт [comparison-analysis-report.json](../verification/comparison-analysis-report.json) только после проверок; исходные работы, фото и комментарии в него не попадают. Версии моделей и даты запусков остаются неизвестными.

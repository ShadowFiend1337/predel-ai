# Бизнес-правила и таблицы решений

Разделы с пометкой «Целевое правило» задают требуемое поведение. Таблица реализации служит точным описанием существующего алгоритма. Это две версии правил, а не взаимозаменяемые утверждения.

## Общие правила

| ID | Правило |
|---|---|
| BR-001 | Варианты `ege13`, `ege14`, `ege15` используют специализированную проверку; остальные — прежнюю. |
| BR-002 | Максимальный балл определяется сервером: №13 — 2, №14 — 3, №15 — 2. Клиент его не переопределяет. |
| BR-003 | Целевое правило: исходная запись неизменяема; OCR и техническая нормализация не исправляют математические ошибки ученика. Превышение предела длины (проектное значение — 40 000 символов) отклоняется с HTTP 422 до оценивания, без молчаливого обрезания. |
| BR-004 | Число модели проверяется и пересчитывается по статусам критериев. Для целевого контракта набор критериев точен, ID уникальны, обоснования непусты. |
| BR-005 | Условия вызова арбитра, защитные ветки и резервный результат задаются таблицами ниже. |
| BR-006 | Целевое правило: при отказе одного оценщика результат второго является предварительным и требует ручной проверки. |
| BR-007 | Целевое правило: при отказе обоих оценщиков и отсутствии отдельно подтверждённого результата оценка отсутствует; технический код не становится баллом. |
| BR-008 | `unknown` программной проверки не является доказательством математической ошибки. |
| BR-009 | `is_solved=true` допускается только при полном окончательном балле без необходимости ручной проверки. |
| BR-010 | Для №14 оценка выполненного пункта б) зависит от его независимости от непринятого доказательства пункта а). |
| BR-011 | Промежуточные результаты и происхождение изменений сохраняются в пределах принятой политики хранения. |
| BR-012 | Один итоговый ответ без требуемого хода решения не засчитывается; этот предметный отказ отличается от технического сбоя. Баллы верхнего уровня и внутри ответа должны совпадать. |

Максимальные баллы и критерии здесь соответствуют конфигурации проекта; методист отвечает за их актуальность относительно выбранной версии официальных критериев.

## BR-010. Зависимость пунктов №14 — реализация

При `K1=not_met` и `K2=met` пересчёт использует следующую таблицу до последующих правил калибровки:

| `part_b_dependency.status` | Балл |
|---|---:|
| `independent` | 2 |
| `uses_proved_part_a`, `uses_unproved_or_wrong_part_a`, `no_part_b_or_unclear`, `unknown` либо отсутствующее значение | 1 |

Для остальных сочетаний критериев действует таблица соответствующего задания. Сочетание непринятого пункта а) со значением `uses_proved_part_a` противоречиво по смыслу; текущая функция всё равно применяет резервный балл 1. В целевом процессе такая неопределённость требует проверки основания, а не автоматического утверждения результата.

## Вызов арбитра — реализация

Условия применяются сверху вниз; сравниваются оценки после их валидации, пересчёта и внутренней калибровки.

| A | B | Дополнительное условие | Действие |
|---|---|---|---|
| Ошибка | Ошибка | — | Базовый балл 0 и признак ручной проверки |
| Ошибка | Успех | — | Взять B и установить признак ручной проверки |
| Успех | Ошибка | — | Взять A и установить признак ручной проверки |
| Успех | Успех | Баллы равны, №13 | Принять общий балл без арбитра |
| Успех | Успех | Баллы равны максимальному | Принять общий балл без арбитра |
| Успех | Успех | Баллы равны, неполный результат №14/15 | Вызвать арбитра |
| Успех | Успех | Баллы различаются | Вызвать арбитра |

## Результат арбитра — реализация

| Условие | Результат до окончательной калибровки |
|---|---|
| Арбитр валиден; A/B совпали по баллу и статусам критериев; арбитр понижает балл | Сохранить общий балл A/B; ответ арбитра оставить в данных проверки; ручная проверка не включается этой веткой |
| Арбитр валиден; защитное условие выше не выполнено | Принять пересчитанный и откалиброванный балл арбитра |
| Арбитр недоступен; A/B равны | Сохранить общий балл |
| Арбитр недоступен; разница A/B равна 1 | Взять минимум без обязательной ручной проверки |
| Арбитр недоступен; разница A/B больше 1 | Взять минимум и установить признак ручной проверки |

После этой таблицы выполняются итоговая калибровка №13/15 и, в обработчике API, учёт OCR-неопределённости. Калибровка может изменить балл и снять признак ручной проверки. При принудительной OCR-маршрутизации текущий API заменяет публичный балл на 0. Таким образом, таблица A/B не является единственным источником окончательного ответа.

## Целевая политика спорных и технических результатов

| Ситуация | Балл | Окончательность | Действие |
|---|---|---|---|
| Результат принят, существенной неопределённости нет | Вычисленный | Окончательный | Опубликовать |
| Один оценщик недоступен | Балл доступного оценщика | Предварительный | Создать ручную проверку |
| Арбитр требовался по правилам, но недоступен | Общий балл при равенстве A/B; минимум при различии | Предварительный | Создать ручную проверку, в том числе при равном неполном балле №14/15 |
| Защитная ветка сохраняет A/B вопреки понижению арбитра | Общий балл A/B | Предварительный | Сохранить конфликт и создать ручную проверку |
| Существенный OCR-конфликт | Предварительная оценка, только если она осмысленна; иначе `null` | Не окончательный | Передать исходную запись куратору; не обнулять её оценку как математический вывод |
| Оба оценщика недоступны, подтверждённого результата нет | `null` | Оценка не получена | Завершить технической ошибкой и разрешить новую попытку |
| Подтверждено отсутствие требуемого хода решения | 0 | Окончательный предметный результат | Объяснить необходимость хода решения |

Целевое правило приоритета: сначала проверяется доступность достоверных исходных данных; затем допустимость математического вывода; затем окончательность оценки. Калибровка не отменяет техническую неопределённость только потому, что найден знакомый текстовый шаблон. Изменение предварительного балла не означает автоматическое утверждение результата.

## Целевые правила интеграции

**BR-P-001 — ручное решение.** Очередь и переход в `needs_curator_review` сохраняются согласованно. Сообщение «передано куратору» допускается только после создания задачи. При изменении балла или пояснений обязательна причина; автоматический результат не перезаписывается. Доступ к записи имеет назначенный куратор либо администратор.

**BR-P-002 — идемпотентность.** Ключ уникален в пределах `lms_client_id`. Повтор того же нормализованного тела возвращает ту же проверку; тот же ключ с другим телом — HTTP 409. Конкурентное создание защищено уникальным ограничением БД. Для первой целевой версии ключ сохраняется на весь срок хранения проверки; повтор истёкшего ключа не гарантирует дедупликацию. Политику хранения согласуют отдельно.

**BR-P-003 — конкурентное редактирование.** Клиент передаёт ожидаемую версию записи. Обновление выполняется только при совпадении версии и допустимом состоянии; иначе 409. Подтверждение результата и изменение состояния сохраняются атомарно.

## Управление правилами

Для изменения нужны ID, владелец, версия, предметная область, условие, приоритет относительно других правил, примеры применения и неприменения, критерий приёмки. Источник балла хранится отдельно от окончательности результата.

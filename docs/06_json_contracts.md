# Контракты API и компонентов

Названия полей и значения перечислений сохранены из кода. Пояснения написаны по-русски. **Реализация** обозначает действующую структуру; **аналитическое представление** объединяет данные для объяснения; **целевая модель** описывает новый интерфейс. Все примеры синтетические.

Применение текстовой отправки и публичного результата в пользовательском сценарии описано в [UC-01](03_use_case_text_submission.md). Его целевые гарантии не изменяют статус действующих контрактов C-01 и C-08.

## C-01. Действующий API

Две текстовые операции формализованы в [OpenAPI текущего API](../contracts/openapi-current.yaml). Условия и результаты их проверки — в [протоколе UC-01](12_api_verification_protocol.md). Файловые операции в эту спецификацию не входят.

Все операции требуют аутентификации пользователя. Для отправки применяется ограничитель частоты запросов; реализационные особенности описаны в NFR-SEC-02.

| Операция | Запрос | Успешный ответ |
|---|---|---|
| `POST /api/submit` | JSON: `task_id`, `text` | HTTP 200, C-08 |
| `POST /api/submit/photo` | `multipart/form-data`: `task_id`, `file` и/или `files` | HTTP 200, C-08 |
| `POST /api/submit/extract_text_from_file` | `multipart/form-data`: `file` | HTTP 200, JSON-строка с извлечённым текстом |
| `GET /api/tasks/{task_id}/attempts` | `limit` 1–200, по умолчанию 50; `offset` ≥ 0, по умолчанию 0 | HTTP 200, массив C-08 только текущего пользователя |

Текстовая отправка:

```json
{
  "task_id": "task-13-001",
  "text": "cos(2x)=0; далее приведён ход решения"
}
```

| Поле | Тип | Обязательность и проверка |
|---|---|---|
| `task_id` | Строка | Обязательно; задача должна существовать в каталоге |
| `text` | Строка | Обязательно, длина ≥ 1; пробельная строка отклоняется обработчиком |
| `file` | Двоичный файл | Для файловой отправки требуется хотя бы один файл |
| `files` | Массив файлов | Можно передать несколько файлов; при наличии `file` он добавляется после `files` |

Максимум на файл — **10 485 760 байт (10 MiB)**. Изображения: PNG, JPG/JPEG, WEBP, GIF, BMP. Текстовые файлы: TXT, MD, TEX, CSV, JSON. PDF поддерживается извлечением текстового слоя; скан без текста не проходит OCR страниц автоматически. Каждый файл проверяется и затем обрабатывается последовательно; текст объединяется в порядке входного списка. Проверка всего пакета до первого OCR сейчас отсутствует; это целевая гарантия FR-003. Обработчик учитывает расширение и MIME-тип. Общий лимит числа файлов отдельно не задан; функция `_trim_text` обрезает как извлечённый, так и введённый текст до настроенного предела, по умолчанию 40 000 символов. В текущем API это обрезание, а не отклонение слишком длинного запроса. Целевое правило BR-003 требует явной ошибки вместо потери части решения.

### Известные ответы с ошибкой

| Условие | HTTP | Примечание |
|---|---:|---|
| Пользователь не аутентифицирован | 401 | Ответ механизма аутентификации |
| Нет задачи в каталоге | 404 | Отправка текста, файлов и история |
| Отсутствуют обязательные поля или непригоден текст | 422 | Ошибка схемы или обработчика |
| Нет файлов, пустой файл, не удалось прочитать PDF | 400 | Файловые операции |
| Превышен размер файла | 413 | Файловые операции |
| Неподдерживаемый формат | 415 | Файловые операции |
| Текст извлечь невозможно | 422 | Включая PDF без текста |
| Ошибка внешнего OCR | 502 | Если ошибка не классифицирована как невозможность извлечь текст |
| Истёк срок извлечения в `/photo` | 504 | Не общий предел времени всей проверки |
| Превышена частота отправок | 429 | Ограничитель отправки |

Ошибки обработчика обычно имеют `{"detail":"..."}`, а ошибки валидации FastAPI — массив деталей. В текущем специализированном оценивании техническая неудача может возвращаться как HTTP 200 с сохранённой попыткой и признаком ручной проверки. Целевое поведение FR-011 отделяет такой случай от математической оценки; оно не выдаётся за действующий контракт.

## C-02. Контекст проверки

Аналитическое представление, не отдельный объект API:

```json
{
  "catalog_task_id": "task-13-001",
  "grading_task_number": "13",
  "prompt_variant": "ege13",
  "task_text": "Синтетическое условие",
  "reference_solution": "Синтетическое эталонное решение",
  "max_score": 2,
  "submission_type": "text"
}
```

Идентификатор каталога и номер задания ЕГЭ — разные понятия. Во внутренних вызовах специализированной проверки поле `task_id` содержит строку `"13"`, `"14"` или `"15"`; во внешнем API — ID задачи каталога. ID попытки создаётся при сохранении и не является обязательным входом оценивания.

## C-03. Извлечённая запись

Сведения об изображении, вариантах распознавания и конфликтах распределены по промежуточным данным. Следующая форма используется только для объяснения:

```json
{
  "transcript_text": "cos(2x)=0",
  "selected_source": "primary",
  "candidates": [{"candidate_id": "primary", "text": "cos(2x)=0"}],
  "conflict_detected": false
}
```

Выбранная запись должна происходить из реально полученного варианта или проверки исходного изображения. Целевой контракт хранит исходную запись и подтверждённые исправления раздельно. Отсутствие признака конфликта не доказывает правильность OCR.

## C-04. Разбор шагов — реализация

Вход `StepParserInput`: `task_id`, `official_problem_text`, `normalized_latex`, `transcript_text`, `transcript_blocks`, `visual_math_facts`. Должен присутствовать текст, блоки или визуальные факты. `prompt_variant` используется обработчиком для настройки разбора, но не является полем модели `StepParserInput`.

Минимальный допустимый результат:

```json
{
  "task_id": "13",
  "steps": [
    {
      "step_id": "s1",
      "order_index": 1,
      "type": "equation_setup",
      "statement_text": "cos(2x)=0",
      "relation_to_previous": "start",
      "evidence_block_ids": [],
      "evidence_visual_fact_ids": [],
      "depends_on_step_ids": [],
      "confidence": 0.96,
      "flags": [],
      "review_required": false
    }
  ],
  "parser_flags": [],
  "confidence": 0.96,
  "review_required": false,
  "flags": []
}
```

0.96 — демонстрационное значение, не измерение качества. `confidence` находится в диапазоне [0, 1]. Обязательные поля шага: `step_id`, `order_index`, `type`, `relation_to_previous`, `confidence`. Полный набор полей, значений и значений по умолчанию представлен в [JSON Schema](../contracts/parsed-steps.schema.json).

`order_index` — целое от 1. `depends_on_step_ids` содержит ссылки на предшествующие шаги. Поля `statement_text`, `statement_latex`, `normalized_statement` представляют разные формы записи. `type` включает, например, `equation_setup`, `equivalent_transformation`, `final_answer`; полного значения `equation_transformation` в схеме нет.

Pydantic проверяет структуру, а прикладной валидатор дополнительно проверяет порядок, ID и зависимости. Сама JSON Schema не доказывает ссылочную целостность или математическую корректность.

## C-05. Программная проверка — реализация

Геометрический аудит возвращает сведения о подтверждённых фактах, вычислительных проверках и отклонённых возражениях. Это отдельная структура; её не следует смешивать с результатом проверки №13.

`Task13VerifierResult`:

```json
{
  "part_a_status": "unknown",
  "part_b_status": "unknown",
  "missing_roots": [],
  "extra_roots": [],
  "critical_algebra_error": false,
  "confidence": 0.0,
  "details": "Синтетический пример неподдерживаемой формы условия"
}
```

Статусы: `verified` — подтверждено, `failed` — обнаружено несоответствие, `unknown` — вывод не получен. `details` — **строка**, а корни представлены массивами строк. `failed` здесь не равен технической ошибке компонента. Общее качество системы не вычисляется из `confidence` этой проверки.

## C-06 и C-07. Ответ оценщика и арбитра — реализация

```json
{
  "criteria": [
    {"id": "K1", "status": "met", "reason": "Уравнение решено корректно."},
    {"id": "K2", "status": "not_met", "reason": "Отбор корней отсутствует."}
  ],
  "score": 1
}
```

Для №14 используется дополнительное поле:

```json
{
  "part_b_dependency": {
    "status": "independent",
    "reason": "Расчёт не использует недоказанное утверждение пункта а)."
  }
}
```

Второй пример — только дополнительный фрагмент, а не полный ответ. Допустимые статусы критериев: `met`, `partial`, `not_met`. Отсутствующие обязательные критерии отклоняются; неизвестные критерии текущий валидатор удаляет. Наличие `reason` проверяется, непустота — пока нет. Значения `part_b_dependency.status`: `independent`, `uses_proved_part_a`, `uses_unproved_or_wrong_part_a`, `no_part_b_or_unclear`, `unknown`. Отсутствующая зависимость пункта б) нормализуется в `unknown`; пересчёт для №14 описан BR-010. Целевая строгая проверка задана FR-009.

Сервер пересчитывает балл по критериям и выполняет калибровку. В сохранённом `GraderResult` отдельно представлены `score`, `llm_score`, `criteria`, `raw_response`, `retries`, `error`, `metadata`. После исчерпания попыток внутренний `score=-1` обозначает техническую неудачу и не является публичной оценкой.

Ответ арбитра имеет ту же предметную структуру. Поля выбора оценщика, происхождения итогового решения и необходимости куратора не следует приписывать ответу модели: они формируются обработчиком.

## C-08. Публичная попытка — реализация

```json
{
  "id": "attempt-example",
  "task_id": "task-13-001",
  "solution_text": "Синтетический ход решения",
  "feedback": {
    "spans_detail": [],
    "checked": true,
    "general_comment": "Отбор корней отсутствует.",
    "comments": [],
    "score": 1,
    "max_score": 2,
    "final_decision": "AUTO_ACCEPT",
    "needs_curator": false,
    "review_required": false,
    "review_reason": "",
    "uncertainty_point": null
  },
  "created_at": "2026-09-14T10:00:00Z",
  "score": 1,
  "max_score": 2,
  "is_solved": false,
  "needs_curator": false,
  "review_reason": "",
  "uncertainty_point": null,
  "coins_rewarded": 0,
  "stats": null
}
```

Обязательные поля модели: `id`, `task_id`, `feedback`, `created_at`; остальные имеют значения по умолчанию. `score` и `max_score` допускают `null`. `final_decision` допускает `AUTO_ACCEPT`, `MANUAL_REVIEW_REQUIRED`, `null`. Эти значения обозначают маршрут, а не математическую правильность. Внутреннее поле `feedback.spans` исключено из публичной сериализации.

[Полная JSON Schema ответа](../contracts/attempt-out.schema.json). Формирование и проверка межполевых инвариантов выполняются прикладным кодом; схема сама по себе не гарантирует равенство дублирующихся баллов. Целевые гарантии определены FR-011, FR-013 и BR-009.

## C-09. Единая запись этапа — целевая модель

```json
{
  "schema_version": "1.0",
  "check_id": "check-example",
  "layer": "grader_a",
  "status": "completed",
  "execution_attempt": 1,
  "started_at": "2026-09-14T10:00:00Z",
  "completed_at": "2026-09-14T10:00:01Z",
  "latency_ms": 1000,
  "result": {"score": 1},
  "error": null
}
```

Статусы: `pending`, `running`, `completed`, `failed`, `skipped`. Для `failed` обязателен безопасный объект ошибки с `code`, `stage`, `retryable`; `result` может отсутствовать. Для `completed` обязателен результат, соответствующий схеме конкретного этапа. Поле `execution_attempt` различает повторные исполнения.

## C-10. Интеграция с LMS — целевая модель

### Создание

`POST /checks`, JSON; обязательные заголовки `Authorization: Bearer <integration-token>` и `Idempotency-Key`. Клиент определяется по учётным данным, а не по произвольному ID в теле.

```json
{
  "schema_version": "1.0",
  "external_submission_id": "lms-example-001",
  "task_id": "task-13-001",
  "solution": {"type": "text", "text": "Синтетический полный ход решения"}
}
```

Обязательны `schema_version`, `task_id`, `solution.type`, `solution.text`. `external_submission_id` необязателен. Для версии 1.0 поддерживается `type=text`, непустой текст до 40 000 символов без молчаливого обрезания. Каталог задач согласован с LMS; условие и эталон из запроса не принимаются. Это проектные параметры внешнего API, не ограничения действующего `POST /api/submit`.

HTTP 202 после надёжного сохранения:

```json
{
  "schema_version": "1.0",
  "check_id": "check-example",
  "status": "received",
  "result": null,
  "error": null
}
```

В ответе также возвращается `Location: /checks/check-example`. При эквивалентном повторе возвращаются тот же ID и актуальное состояние: 202 для незавершённой проверки, 200 для терминальной. Другой запрос с тем же ключом — 409. Неавторизованный клиент — 401; неподдерживаемая версия или невалидный вход — 422; неизвестная задача — 404; превышение частоты — 429. Лимит частоты внешней интеграции согласуется отдельно.

Эквивалентность определяется по распознанному JSON: порядок полей и пробелы вне строк не учитываются; значения строк, включая текст решения, сравниваются без смысловой нормализации и обрезания. Неизвестные поля отклоняются с 422. `external_submission_id`, если передан, должен быть непустой строкой; `null` не равнозначен отсутствующему полю и отклоняется. Хеш вычисляется по канонической записи принятых полей; область уникальности ключа определяется клиентом.

### Получение состояния

`GET /checks/{check_id}` возвращает HTTP 200 для своей проверки; чужой или отсутствующий ID — 404.

```json
{
  "schema_version": "1.0",
  "check_id": "check-example",
  "external_submission_id": "lms-example-001",
  "status": "needs_curator_review",
  "result": {
    "score": 1,
    "max_score": 2,
    "result_status": "provisional",
    "verdict": "partially_correct",
    "student_feedback": {"general_comment": "Оценка требует подтверждения.", "comments": []},
    "decision": {
      "source": "grader_a",
      "requires_curator_review": true,
      "review_reason_codes": ["GRADER_UNAVAILABLE"]
    }
  },
  "error": null,
  "created_at": "2026-09-14T10:00:00Z",
  "updated_at": "2026-09-14T10:00:03Z"
}
```

Статусы проверки и переходы определены [моделью состояний](../diagrams/state_diagram.md): `received`, `processing`, `completed`, `needs_curator_review`, `under_review`, `reviewed`, `failed`. Отмена и повторное открытие в первую версию не входят.

| Состояние | Результат |
|---|---|
| `received`, `processing` | `result=null`, `error=null` |
| `completed`, `reviewed` | Числовой балл 0…`max_score`, `result_status=final`, ручная проверка не требуется |
| `needs_curator_review`, `under_review` | `result_status=provisional`; балл может быть числом или `null` при недостаточных данных |
| `failed` | `result=null`, обязателен `error`; математическая оценка не подставляется |

`verdict`: полный балл → `correct`, ненулевой неполный → `partially_correct`, ноль → `incorrect`, отсутствие оцениваемого результата → `not_evaluable`. Предварительный `verdict` не считается утверждённым. `decision.source`: `primary_agreement`, `grader_a`, `grader_b`, `arbiter`, `calibration`, `curator`, `none`.

### Технический отказ

```json
{
  "schema_version": "1.0",
  "check_id": "check-example",
  "status": "failed",
  "result": null,
  "error": {
    "code": "GRADING_UNAVAILABLE",
    "stage": "evaluation",
    "message": "Не удалось завершить автоматическую проверку. Можно отправить решение повторно.",
    "retryable": true
  }
}
```

Повтор с прежним ключом возвращает прежнюю проверку. Для сознательного запуска новой попытки после `failed` клиент создаёт новый ключ. До завершения срока хранения ключа это не меняет правило идемпотентности.

## C-11. Целевой синхронный API сайта 2.0

`POST /api/v2/submit` возвращает сохранённый `AttemptV2`; `GET /api/v2/tasks/{task_id}/attempts` — собственные попытки этой версии. Точная схема и примеры: [OpenAPI 2.0](../contracts/openapi-target-v2.yaml). [Описание API](11_api_specification.md) задаёт проверку входа, ошибки, окончательность, правила повторной отправки и сопоставление с данными.

Балл находится в единственном поле `score`; `result_status` отличает `final` от `provisional`. Предварительный результат требует ID сохранённой задачи куратора. Техническая ошибка содержит `result=null`, безопасный код и ID запроса; балл при этом отсутствует. Ошибка без пригодной оценки — 503 `GRADING_UNAVAILABLE`; подтверждённый отказ записи — 500 `PERSISTENCE_FAILURE`.

Это отдельный контракт сайта, а не новая редакция LMS-контракта C-10 с `schema_version=1.0`. В текущем backend маршруты v2 отсутствуют. [Коллекция Postman](../postman/uc01-target-v2.postman_collection.json) задаёт будущую приёмку; выполнены проверки структуры и примеров, но не целевого сервера.

## Версионирование и доступ

API-схема, набор критериев, промпт и маршрут проверки версионируются раздельно. Несовместимое изменение обязательных полей или допустимых значений требует новой основной версии. Добавление необязательного поля допустимо в совместимой версии, если потребители допускают неизвестные поля.

Публичный ответ не включает исходные ответы провайдера, секреты и внутренние промпты. Доступ к исходным работам и промежуточным результатам ограничивается ролью и принадлежностью проверки. Сроки хранения согласуются отдельно.

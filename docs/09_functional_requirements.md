# Функциональные требования

Требования ниже задают целевое поведение. Фактическое выполнение и ограничения приведены в [матрице реализации](20_implementation_status.md). Приоритет MoSCoW не равен статусу реализации: Must — обязательно для указанной версии; Should — желательно; Could — допустимое расширение; Won’t — вне её границ.

## Основной сценарий

| ID | Требование | Приоритет |
|---|---|---|
| FR-001 | Система должна выбирать специализированную проверку для `ege13`, `ege14`, `ege15` и прежний механизм для остальных вариантов. | Must |
| FR-002 | Система должна принимать текст или поддерживаемые файлы решения; формат и ограничения определены контрактом C-01. | Must |
| FR-003 | До вызовов ИИ система должна проверить обязательные поля, наличие задачи, непустое содержимое, допустимую длину текста, формат и размер файлов. | Must |
| FR-004 | Для изображения система должна получить текст распознавания и сохранить сведения об источнике выбранного варианта. | Must |
| FR-005 | Система должна сохранять исходную запись ученика; нормализация и OCR не должны автоматически исправлять её математический смысл. | Must |
| FR-006 | Для специализированной проверки система должна сформировать структурированные шаги; при невозможности — сохранить причину и перейти к допустимому резервному сценарию. | Must |
| FR-007 | Программная проверка должна возвращать `unknown`, если вход выходит за область её применимости; этот результат не должен сам по себе снижать балл. | Must |
| FR-008 | Оценщики A/B должны получать одинаковый контекст независимо друг от друга; конфигурация должна определять последовательный или параллельный запуск. | Must |
| FR-009 | Система должна проверять структуру ответов, уникальность и состав критериев, допустимость статусов и непустоту обоснований, затем пересчитывать балл по правилам. | Must |
| FR-010 | Система должна вызывать арбитра и выбирать результат согласно полной таблице решений BR-005. | Must |
| FR-011 | Система должна различать вычисленную оценку, предварительную оценку и невозможность оценки; технический отказ не должен публиковаться как математический ноль. | Must |
| FR-012 | Калибровка должна иметь явное условие, приоритет и сохраняемое происхождение изменения. | Should |
| FR-013 | Ответ должен содержать согласованные баллы, пояснения, статус окончательности и причину ручной проверки, если она требуется. | Must |
| FR-014 | Система должна сохранять попытку и её промежуточные результаты одной операцией БД. | Must |
| FR-015 | Синхронный API должен возвращать успешный результат после сохранения попытки. | Must |
| FR-016 | Отправка решений должна требовать аутентификации и ограничения частоты запросов. | Must |

При отправке только ответа без хода решения система применяет отдельное правило BR-012. Такой случай не является техническим отказом. Необходимость проверки куратором и обещание уже созданной задачи различаются по BR-P-001.

## Интеграция с LMS и ручная проверка — целевая версия

| ID | Требование | Приоритет |
|---|---|---|
| FR-P-001 | API должен надёжно сохранять принятую проверку, возвращать HTTP 202 и `check_id`, а вычисление выполнять асинхронно. | Must |
| FR-P-002 | API должен возвращать состояние и доступный результат по `check_id` только клиенту-владельцу. | Must |
| FR-P-003 | Если результат требует ручной проверки, система должна сохранить связанную задачу куратора до подтверждения передачи. | Must |
| FR-P-004 | Назначенный куратор должен иметь возможность подтвердить или изменить балл и пояснения; конфликт версий должен отклонять запись. | Must |
| FR-P-005 | Ручное решение должно сохранять автора, время, причину изменения и неизменяемый исходный автоматический результат. | Must |
| FR-P-006 | Клиент должен получать результат через polling. Webhook рассматривается отдельно после согласования доставки. | Must / Could |
| FR-P-007 | Создание проверки должно быть идемпотентным в пределах клиента согласно BR-P-002. | Must |

## Готовность требования

Для постановки в разработку определены источник, версия, входы и выходы, основной и ошибочные сценарии, связанные правила, критерии приёмки и способ проверки. Неизвестный параметр фиксируется как вопрос с ответственным, а не подменяется достигнутым показателем.

# UC-01. Отправка решения текстом

Use Case описывает целевое поведение: ученик отправляет развёрнутое решение на сайте и получает сохранённую оценку с пояснениями либо понятное сообщение о причине, по которой окончательная оценка не получена.

## Паспорт сценария

| Поле | Значение |
|---|---|
| Идентификатор | UC-01 |
| Версия и дата | 1.1; 15 сентября 2026 года |
| Статус | Целевой сценарий; соответствие коду отражено в [матрице реализации](20_implementation_status.md) |
| Уровень | Пользовательская цель |
| Основной участник | Ученик |
| Система | PredelAI: сайт, API, компоненты проверки и хранение |
| Внешняя зависимость | Провайдер языковых моделей |
| Дополнительный участник | Куратор — получает задачу только в расширении А7; само ручное оценивание вне этого сценария |
| Цель ученика | Узнать оценку решения и понять, какие ошибки нужно исправить |
| Основание | BG-01, BG-03, BG-04; US-ST-02–US-ST-05 |
| Триггер | Ученик нажимает кнопку отправки введённого решения |
| Канал | Сайт → целевой синхронный `POST /api/v2/submit`; текущий маршрут — `/api/submit` |
| Основной предметный охват | Задания с вариантом `ege13`, `ege14`, `ege15`; иной вариант обрабатывается по А1 |
| Вне границ | Загрузка файлов и OCR, регистрация, изменение каталога задач, ручное оценивание после назначения, внешняя интеграция LMS |

Сайт, API и база данных входят в границу системы и не считаются самостоятельными пользователями. Целевые состояния `CheckJob` из интеграции LMS не являются статусами действующего синхронного запроса.

## Предусловия

1. Ученик открыл страницу выбранной задачи; сайт располагает её идентификатором каталога.
2. Ученик ранее вошёл в систему. Действительность авторизации проверяется сервером при отправке; истечение сессии обрабатывается по Е1.
3. На странице доступно поле для текстового решения и действие отправки.

Валидность текста, существование задачи на момент запроса и доступность компонентов проверяются в ходе сценария. Они не предполагаются заранее: для их нарушения предусмотрены ошибочные ветви.

## Вход и результаты

| Данные | Правило |
|---|---|
| `task_id` | Обязательная строка — ID задачи каталога, а не номер задания ЕГЭ |
| `text` | Обязательная строка с решением. Пробельный ввод недопустим; проектный предел — 40 000 символов по BR-003. Превышение отклоняется без обрезания |
| Автор запроса | Определяется по авторизации; произвольный идентификатор пользователя в теле не определяет владельца попытки |
| Условие, эталон, критерии, максимальный балл | Определяются сервером по задаче и конфигурации; ученик их не переопределяет |

Подсчёт длины выполняется по символам исходной строки, включая пробелы и переводы строк, до технической нормализации. Непустота проверяется отдельно: строка должна содержать хотя бы один непробельный символ. Исходная запись и подготовленное для проверки представление различаются.

| Исход | Что получает ученик | Что подтверждено системой |
|---|---|---|
| Окончательная оценка | Балл, максимум и пояснения | Попытка и основания результата сохранены |
| Предварительный результат | Явную отметку, что оценка не окончательная, и причину ручной проверки | По А7 сохранены предварительный результат и связанная задача куратора |
| Отклонённый запрос | Причину отказа и возможность исправить вход | Оценивание не запускалось, новая попытка не создана |
| Техническая невозможность оценки | Сообщение об отсутствии оценки и следующий шаг | Математический балл не подставлен вместо ошибки |
| Исход неизвестен клиенту | Сообщение, что получение ответа не подтверждено | Клиент не делает вывод об отсутствии сохранённой попытки; применяется Е7 |

Это предметные исходы Use Case. Формат существующего запроса определён в C-01, успешного ответа — в C-08. Требования к отсутствующей и предварительной оценке задаёт FR-011. Целевой формат сайта закреплён в C-11 и [спецификации API](11_api_specification.md). Он не переносит поля интеграционного C-10 в действующий `AttemptOut` и не объявляет новые схемы уже реализованными.

## Основной ход

Основной ход заканчивается окончательной автоматической оценкой. Она может быть нулевой, неполной или максимальной: успешное выполнение сценария означает получение корректно оформленного результата, а не правильность решения ученика.

| Шаг | Участник | Действие и наблюдаемый результат |
|---:|---|---|
| 1 | Ученик | Вводит ход решения и отправляет его на проверку. |
| 2 | Сайт | Передаёт `task_id` и `text` в целевой `POST /api/v2/submit`; показывает, что запрос выполняется. Пока запрос ожидается, повторное нажатие не создаёт вторую отправку. |
| 3 | API | Проверяет авторизацию, ограничение частоты, структуру и допустимость входа, получает задачу каталога. До завершения этих проверок вызовы моделей не выполняются. |
| 4 | Система | Сохраняет исходную запись в контексте обработки; отдельно готовит техническое представление без исправления математического смысла. При сохранении попытки на шаге 11 исходная запись сохраняется вместе с ней. |
| 5 | Система | По метаданным задачи выбирает специализированный маршрут, критерии и максимальный балл. |
| 6 | Система | Проверяет наличие требуемого хода решения. В основном ходе запись содержит решение, пригодное для оценивания. |
| 7 | Система | Формирует шаги и зависимости, проверяет их структуру; выполняет применимые программные математические проверки. Полученные факты и неопределённость включаются в контекст оценивания. |
| 8 | Система | Передаёт общий контекст независимым оценщикам A/B. Проверяет ответы, при необходимости выполняет ограниченные повторы; пересчитывает и калибрует каждый балл по правилам. |
| 9 | Система | Сравнивает оценки. Если BR-005 требует арбитра, получает и проверяет его ответ, затем выбирает результат. В основном ходе существенная неопределённость разрешена. |
| 10 | Система | Применяет итоговые правила и формирует оценку, её происхождение, окончательность и пояснения. Проверяет согласованность полей; вычисляет `is_solved` по BR-009. |
| 11 | Система | Сохраняет попытку, принадлежность ученику, исходную запись, итог и промежуточные результаты. Подтверждает успешную фиксацию данных. |
| 12 | API | Возвращает HTTP 200 по C-11 с идентификатором сохранённой попытки, баллом, максимумом, `result_status=final` и пояснениями. |
| 13 | Сайт | Завершает ожидание и показывает окончательный результат. Ученик видит оценку и пояснения к своей работе. |

Внутренние действия шагов 7–10 раскрыты в [спецификации этапов](05_layer_specifications.md) и [таблицах решений](18_business_rules_and_decision_tables.md). Сценарий не вводит вторую версию алгоритма A/B и арбитра.

## Альтернативные ходы

Альтернатива указывает точку ответвления, действия и место возврата либо завершения. Несколько альтернатив могут возникнуть в одной проверке: например, А3 → А5 → А7.

| Ветвь | Условие и шаг | Действия | Продолжение |
|---|---|---|---|
| А1. Иной вариант задания | Шаг 5: вариант не входит в `ege13`–`ege15` | Система проверяет наличие хода решения. Если оно есть, использует прежний механизм и разбирает его ответ с маркерами. Специализированные шаги 7–9 не выполняются. | При пригодном результате — шаг 10; только ответ — А2; неразрешённая техническая ошибка — Е5 |
| А2. Только итоговый ответ | Шаг 6 либо А1: подтверждено отсутствие требуемого хода решения | По BR-012 система формирует предметный результат 0 с максимумом задачи и пояснением «Нужен полный ход решения». Вызовы оценщиков не требуются. | Шаг 10, затем сохранение и показ результата; это не технический сбой |
| А3. Разбор шагов не дал результата | Шаг 7: разбор непригоден после разрешённых резервных действий | Система фиксирует причину и продолжает работу с исходной записью без выдуманных шагов. Программные проверки выполняются только в пределах применимости имеющихся данных. | Оставшаяся часть шага 7, затем шаг 8 |
| А4. Программная проверка неприменима | Шаг 7: получен `unknown` | Система сохраняет отсутствие вывода. Само значение `unknown` не снижает оценку и не доказывает ошибку ученика. | Шаг 8 |
| А5. Доступен один оценщик | Шаг 8: один оценщик исчерпал попытки, второй дал валидный результат | Система сохраняет оценку доступного оценщика как предварительную и причину неопределённости. Окончательная калибровка не снимает эту неопределённость автоматически. | Шаг 10, затем А7 |
| А6. Требуемое подтверждение не получено | Шаг 9: арбитр недоступен либо его понижение блокируется защитным правилом; или на шаге 10 правило завершилось ошибкой при наличии пригодной предыдущей оценки | Система применяет целевую резервную политику: сохраняет общий балл/минимум A/B либо предыдущую пригодную оценку, причину и предварительность. | Шаг 10 без повторения отказавшего действия, затем А7 |
| А7. Требуется куратор | Шаг 10: результат остаётся предварительным | Система сохраняет предварительный результат и связанную задачу куратора согласованно по BR-P-001. После подтверждения сохранения сообщает, что результат ожидает ручной проверки; предварительный балл не выдаётся за окончательный. | UC завершён передачей на ручную проверку. Действия куратора — отдельный процесс. Ошибка сохранения — Е6/Е7 |

А7 — целевое расширение, зависящее от FR-P-003. Оно не считается работающим только из-за значения `needs_curator=true` в текущем ответе. Предварительный результат может иметь `score=null`, если данных для числовой оценки недостаточно; наличие пригодной исходной работы и основание передачи должны быть зафиксированы.

## Ошибочные ходы

| Ветвь | Условие и шаг | Реакция системы | Завершение и следующий шаг |
|---|---|---|---|
| Е1. Авторизация недействительна | Шаг 3: пользователь не определён или сессия истекла | HTTP 401; модели не вызываются, попытка не создаётся. Сайт сохраняет введённый текст в текущей форме. | Ученик повторно входит в систему и осознанно отправляет решение заново |
| Е2. Превышена частота | Шаг 3: сработал ограничитель | HTTP 429; оценивание не начинается. Сайт сообщает об ограничении без автоматических повторов отправки. | Ученик повторяет действие после снятия ограничения |
| Е3. Недопустимый запрос | Шаг 3: обязательные поля отсутствуют, имеют неверный тип, текст пуст/пробелен либо превышает предел | HTTP 422 с понятной причиной; текст не обрезается и не оценивается. | Ученик исправляет ввод; следующая отправка начинает новый UC |
| Е4. Задача отсутствует | Шаг 3: ID не найден в каталоге | HTTP 404; вызовы моделей не выполняются, попытка не создаётся. | Ученик возвращается к каталогу или обновляет страницу задачи |
| Е5. Оценка не получена | Шаги 7–10 или А1: допустимые способы продолжения исчерпаны; в частности, отказали оба оценщика и иного подтверждённого результата нет | Система формирует безопасное сообщение о технической невозможности оценки и сохраняет диагностику доступным служебным способом. Математический балл отсутствует; передача куратору без задачи не заявляется. | UC завершён без оценки. Повтор допускается после устранения причины; исходный текст остаётся доступен в форме |
| Е6. Сохранение достоверно не выполнено | Шаг 11 или А7: получено подтверждение отката/неуспеха фиксации | Система не возвращает успешный ответ о сохранённом результате и не сообщает о созданной задаче куратора. Сайт объясняет ошибку сохранения. | После восстановления доступности ученик может отправить решение повторно |
| Е7. Неизвестен исход отправки | После шага 2: соединение оборвалось, клиент перестал ждать либо исход фиксации данных не подтверждён | Сайт сообщает, что результат запроса неизвестен; не показывает ложный ноль и не отправляет запрос автоматически повторно. | Ученик открывает историю своих попыток. Если результата пока нет, это не доказывает, что обработка остановилась. Новая отправка — осознанное действие с возможностью второй попытки |

Для Е5 C-11 задаёт HTTP 503, `error.code=GRADING_UNAVAILABLE` и `result=null`. Для Е6 предусмотрены HTTP 500 и `PERSISTENCE_FAILURE`; при неподтверждённой фиксации Е7 — HTTP 503 и `PERSISTENCE_OUTCOME_UNKNOWN` без автоматического повтора. Действующий HTTP 200 с нулём и признаком ручной проверки не выполняет целевой исход Е5. Для всего текстового запроса здесь не задаётся новый числовой предел времени: его согласование относится к NFR-PERF-01.

Для Е7 в C-11 используется `GET /api/v2/tasks/{task_id}/attempts`; для прежних попыток остаётся `GET /api/tasks/{task_id}/attempts`. Это не опрос состояния асинхронного задания. В текущем и целевом синхронных POST не заявлена идемпотентность. Блокировка повторного нажатия на сайте предотвращает часть случайных повторов, но не гарантирует отсутствие дубликатов на сервере. BR-P-002 относится к отдельному целевому API LMS.

## Постусловия и минимальные гарантии

**После окончательной оценки:** сохранена попытка данного ученика; балл находится в диапазоне задачи и согласован между полями; доступны пояснения и основания проверки. `is_solved=true` только при полном окончательном балле без необходимости куратора. Сохранённая попытка доступна в истории.

**После А7:** предварительный результат связан с сохранённой задачей куратора; причина передачи доступна; автоматическая оценка не выдана за утверждённую. Завершение этого UC не означает завершения ручной проверки.

**Для всех исходов:** математическая ошибка ученика не исправляется неявно; технический отказ не превращается в балл; сообщение об успешном сохранении опирается на подтверждённую фиксацию. Публичные ответы не раскрывают служебные промпты, секреты и детали исключений провайдера. Ученик получает только собственные результаты.

При отказе до сохранения не гарантируется наличие новой записи в истории. При неопределённом исходе Е7 не гарантируется её отсутствие. Успешная авторизация и проверка входа сами по себе не подтверждают, что попытка уже сохранена.

## Пример прохождения

Синтетическая задача `demo-ege13-001` должна быть предварительно подготовлена в тестовом каталоге с вариантом `ege13`, максимумом 2 и условием: «а) Решите уравнение 2cos(x) − 1 = 0. б) Найдите его корни на отрезке [0; 2π]». В существующем каталоге этот ID не предполагается.

```json
{
  "task_id": "demo-ege13-001",
  "text": "а) 2cos(x) - 1 = 0, откуда cos(x) = 1/2. Поэтому x = ±π/3 + 2πn, n ∈ Z. б) На отрезке [0; 2π] получаем π/3 и 5π/3. Ответ: а) ±π/3 + 2πn, n ∈ Z; б) π/3, 5π/3."
}
```

Ожидаемый предметный результат — 2 из 2. Для демонстрации основного хода задаются валидные ответы A/B с баллом 2 и выполненными критериями; существенная неопределённость отсутствует. На шаге 9 арбитр пропускается, на шаге 11 данные сохраняются, на шаге 13 ученик видит окончательную оценку 2 из 2 и `is_solved=true`.

Пример иллюстрирует вход и ожидаемое поведение. Его HTTP-часть выполнена с подстановкой результата оценивания на изолированном стенде — см. [протокол](12_api_verification_protocol.md). Этот запуск не подтверждает, что реальные модели вернут указанные оценки.

| Е7 | FR-015, NFR-REL-05, NFR-PERF-01 | Сценарий потери ответа после сохранения: история содержит результат, автоматической повторной отправки нет |

Формулировки поведения сайта в шагах 2 и 13, а также Е1 и Е7 являются целевыми условиями этого UC. Они не помечены как проверенные существующими модульными тестами. Протокол приёмки должен отдельно подтвердить сохранение ввода в форме, индикацию ожидания и обработку потери ответа.

## Связанные модели и граница реализации

- [Контракты](06_json_contracts.md): C-01 — вход и история; C-04–C-07 — внутреннее оценивание; C-08 — структура действующего ответа; C-11 — целевой API сайта 2.0.
- [Диаграмма взаимодействия](../diagrams/pipeline_sequence.md): реализованный синхронный маршрут без файловой ветви; UC задаёт целевое поведение его альтернатив и ошибок.
- [BPMN приёма и проверки](../processes/README.md): общий процесс; для UC-01 входом служит текст, ветвь куратора заканчивается после создания задачи.
- [Модель данных](../diagrams/erd.md): попытка и промежуточные данные; отдельная целевая модель ручной проверки.
- [Модель состояний](../diagrams/state_diagram.md): различие завершённого HTTP-запроса и окончательного результата; состояния ручного процесса.
- [Матрица реализации](20_implementation_status.md): GAP-01, GAP-02, GAP-03, GAP-04, GAP-06–GAP-10 описывают существенные отличия текущего кода от этого сценария. Файловые GAP-05 и GAP-11 в UC-01 не проверяются.

Передача в А7 обеспечивается проектируемой связью `AttemptV2` → `AttemptReview` в ERD сайта. Попытка, задача куратора и событие создания сохраняются согласованно до ответа по C-11. Эта связь пока не реализована в backend; сущности `CheckJob` и `CuratorReview` относятся к отдельной интеграции LMS. Основной автоматический ход не требует создания ручной проверки.

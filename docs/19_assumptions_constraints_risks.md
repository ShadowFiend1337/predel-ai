# Заинтересованные стороны, допущения и риски

## Участники и ответственность

| Участник | Интерес | Решения в его зоне ответственности |
|---|---|---|
| Ученик | Понятная и корректная проверка | Проверка понятности результата и следующего шага |
| Куратор | Полный контекст спорного случая | Подтверждение или изменение оценки |
| Методист | Корректность критериев | Версия правил, экспертная разметка, допустимые способы решения |
| Продуктовая команда | Ценность и стоимость | Приоритеты, допустимый риск, критерии запуска |
| Разработчики | Предсказуемое поведение | Реализация контрактов, надёжность обработки и хранения |
| Школа-партнёр | Качество услуги | Условия пилота и использование данных |
| Владелец LMS | Надёжная интеграция | Идентификаторы, авторизация, доставка и совместимость |
| Ответственный за данные | Управляемая обработка работ | Доступ, сроки хранения и удаление |

## Допущения

| ID | Допущение | Как проверить |
|---|---|---|
| ASM-01 | Условие и эталон каталога корректны | Предметная проверка методистом |
| ASM-02 | Метаданные позволяют определить вариант задания | Проверка каталога и маршрутизации |
| ASM-03 | Историческая выборка пригодна для предварительных выводов | Проверка состава, пропусков и повторяющихся задач |
| ASM-04 | Экспертная оценка может служить эталоном | Независимая разметка и процедура разрешения разногласий |
| ASM-05 | Синхронный сценарий приемлем для сайта | Измерение задержки и наблюдение за использованием |
| ASM-06 | Специализацию можно расширять | Критерии, контрольные примеры и оценка затрат для нового задания |

Допущения не являются установленными фактами. Целевые решения могут быть спроектированы заранее, но их согласование и приёмка фиксируются отдельно.

## Ограничения

Реализованная специализация охватывает №13–15; прежний механизм продолжает работать для остальных вариантов. Вызовы зависят от внешних провайдеров. Программные математические проверки имеют ограниченную область применимости. Текущая БД хранит промежуточные результаты внутри попытки. Рабочий процесс куратора и внешняя LMS-интеграция относятся к целевой модели.

Подробные ограничения API и времени ожидания — в C-01 и NFR; отличия реализации от требований — в отдельной матрице.

## Правило изменения границ

Новый тип задания включается после определения критериев, данных и приёмки. Изменение бизнес-правила требует анализа влияния на контракты, диаграммы, примеры и тесты. Проектное решение не меняет статус на реализованное без подтверждения кодом и проверкой.

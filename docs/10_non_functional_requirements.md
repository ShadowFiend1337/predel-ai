# Нефункциональные требования

NFR задают требуемое качество. Желаемый порог можно сформулировать до измерения исходного уровня: на основании потребности пользователя, бюджета или интеграционного ограничения. Он становится согласованным требованием после решения владельца, а достигнутым показателем — только после проверки.

Для каждого числового порога фиксируются значение, нагрузка или выборка, способ измерения, владелец и статус. Если значение неизвестно, оно помечается TBD с процедурой определения.

## Производительность

| ID | Требование | Статус и проверка |
|---|---|---|
| NFR-PERF-01 | Время ожидания каждого этапа должно быть ограничено; превышение должно иметь определённый результат для клиента. Общий предел времени синхронного запроса задаётся отдельно. | Поэтапные ограничения реализованы; общий предел времени требует изменения и приёмки |
| NFR-PERF-02 | Оценщики A/B должны исполняться параллельно при соответствующей конфигурации. | Реализовано; проверка по вызовам и журналу |
| NFR-PERF-03 | Задержка должна измеряться отдельно для OCR, разбора, A/B и арбитра. | Измеряется частично; полноту измерений проверить |
| NFR-PERF-04 | Целевые p50/p95 определяются для оговорённых типов входа и нагрузки. | TBD; продукт и разработка задают порог, нагрузочный тест проверяет |
| NFR-PERF-05 | Внешний асинхронный API должен подтверждать приём без ожидания проверки ИИ. | Целевая интеграция; PAC-P-04 |

Текущие настройки по умолчанию: извлечение в `/photo` — 180 секунд; внешний предел разбора шагов — 110 секунд; специализированное оценивание — 180 секунд с возможностью настройки по заданию. Это разные последовательно применяемые бюджеты, а не общий SLA. Превышение времени извлечения в `/photo` даёт 504; ошибка оценивания обрабатывается иначе, см. C-01. Нижележащие вызовы имеют собственные ограничения.

## Надёжность

| ID | Требование | Проверка |
|---|---|---|
| NFR-REL-01 | Невалидный ответ модели должен приводить к ограниченным повторам. | Проверки валидации и исчерпания попыток |
| NFR-REL-02 | Отказ разбора шагов должен иметь допустимый резервный сценарий. | LAC-SP-04 |
| NFR-REL-03 | Отказ одного оценщика не должен скрываться в окончательной оценке. | PAC-08 |
| NFR-REL-04 | Отказ обоих оценщиков не должен представляться математическим баллом. | PAC-09 |
| NFR-REL-05 | Успешный ответ о попытке допустим после её сохранения. | PAC-12 |
| NFR-REL-06 | Повторная доставка задания не должна создавать вторую проверку или второй итоговый результат. | PAC-P-05, PAC-P-09 |

## Доступ и защита данных

| ID | Требование | Состояние |
|---|---|---|
| NFR-SEC-01 | Отправка решений требует аутентификации. | Реализовано |
| NFR-SEC-02 | Отправка ограничивается по частоте. | Текущий лимит: 20 запросов за 60 секунд на сочетание пользователя и IP в одном процессе; администратор освобождён. Распределённое ограничение не заявляется |
| NFR-SEC-03 | Секреты, служебные промпты и детали исключений провайдера не передаются клиенту. | Целевое требование; требуется проверка всех ошибочных веток |
| NFR-SEC-04 | Ручное решение доступно назначенному куратору или администратору. | Целевая модель |
| NFR-SEC-05 | LMS использует отдельные учётные данные и получает только свои проверки. | Целевая модель |
| NFR-PRV-01 | В портфолио отсутствуют исходные ученические работы и персональные данные. | Правило публикации |
| NFR-PRV-02 | В модели и журналы передаются только необходимые данные. | Целевое требование |
| NFR-PRV-03 | Для изображений, текста и служебных ответов определены сроки хранения и удаления. | TBD; ответственный за данные и продукт согласуют политику |
| NFR-PRV-04 | История ручных решений хранит идентификатор автора в необходимом объёме. | Целевая модель |

## Наблюдаемость и сопровождение

| ID | Требование | Состояние |
|---|---|---|
| NFR-OBS-01 | Промежуточные результаты позволяют определить этап ошибки. | Реализовано для сохранённых попыток; отказы до сохранения требуют журналирования |
| NFR-OBS-02 | События содержат этап, идентификатор запроса, время, число повторов и исход. | Частично реализовано |
| NFR-OBS-03 | Агрегируются качество, разногласия, ручные проверки, ошибки и затраты. | Целевой сбор метрик |
| NFR-OBS-04 | Объяснимость опирается на входы, результаты, критерии и правила, не требует скрытых рассуждений модели. | Проектное ограничение |
| NFR-OBS-05 | Асинхронная обработка использует сквозной идентификатор. | Целевая интеграция |
| NFR-MNT-01 | У промптов и критериев есть владелец и процедура изменения. | Назначение и регламент требуют согласования |
| NFR-MNT-02 | Версии модели, промпта, критериев, программы и схемы сохраняются с результатом. | Требуется единая реализация |
| NFR-MNT-03 | Бизнес-правила доступны вне текста промпта. | Описаны таблицами; актуальность проверяется при изменении |
| NFR-MNT-04 | Калибровка имеет ID, обоснование, положительные и отрицательные примеры. | Целевая формализация |
| NFR-MNT-05 | Изменения контрактов проверяются у отправителя и получателя. | Проверка схем и контрактные тесты |

## Качество и стоимость

| ID | Требование |
|---|---|
| NFR-QLT-01 | Качество измеряется на независимой экспертной разметке отдельно по типам заданий. |
| NFR-QLT-02 | Измеряются совпадение итогового балла и статусов критериев. |
| NFR-QLT-03 | Отдельно измеряется доля замечаний о несуществующих ошибках. |
| NFR-QLT-04 | Качество OCR отделяется от качества оценивания. |
| NFR-QLT-05 | Совпадение A/B не считается самостоятельным доказательством правильности. |
| NFR-COST-01 | Затраты на ИИ включают все вызовы, повторы и арбитра. |
| NFR-COST-02 | Полная стоимость включает долю ручных проверок и операционные расходы. |
| NFR-COST-03 | Историческая оценка 7 ₽ против 10 ₽ не выдаётся за доказанную полную экономию. |

Числовые пороги качества и стоимости имеют статус TBD. Продукт и методист определяют допустимый риск; измерение на фиксированной выборке показывает достижимость. [Методика расчётов](13_metrics.md).

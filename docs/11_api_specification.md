# API сценария отправки решения

Версия документа: 1.0, 15 сентября 2026 года. Основание — [UC-01](03_use_case_text_submission.md), FR-002, FR-003, FR-013–FR-016 и расширение FR-P-003. Контракты охватывают отправку текста и чтение собственной истории. Загрузка файлов, API куратора и асинхронный API LMS сюда не входят.

Эти форматы не являются сертификатами качества продукта.

## Действующий интерфейс

| Операция | Вход | Успех |
|---|---|---|
| `POST /api/submit` | JSON с `task_id` и `text` | 200, `AttemptOut` |
| `GET /api/tasks/{task_id}/attempts` | ID задачи, необязательные `limit` и `offset` | 200, массив собственных `AttemptOut` |

Обе операции требуют `Authorization: Bearer <токен доступа>`. Refresh-токен не подходит. Автор определяется сервером по токену. Для отправки действует лимит 20 запросов за 60 секунд на пользователя и IP в одном процессе; администратор освобождён. Текущий 429 не содержит `Retry-After`.

`text` обязателен и имеет строковый тип; пустые и пробельные строки отклоняются. Неизвестные поля JSON игнорируются. Превышение длины обработчик обрезает по настройке — по умолчанию до 40 000 символов; затем возможна дополнительная нормализация. Это GAP-01, а не целевое правило приёма. Пример из протокола содержит 40 005 символов; после обрезания и удаления крайнего пробела сохраняются 39 999.

В истории `limit` находится в диапазоне 1–200, по умолчанию 50; `offset` неотрицателен, по умолчанию 0. Пустая собственная история возвращает `[]`, неизвестная задача — 404. История не раскрывает чужие попытки. Максимум в истории извлекается из `feedback`; для ветви «только ответ» верхние поля первоначального ответа и истории могут различаться.

Ошибки авторизации, неизвестной задачи и превышения частоты имеют объект с `detail`-строкой. Ошибка валидации FastAPI содержит `detail`-массив, а отклонение пробельного текста обработчиком — `detail`-строку. Необработанное исключение может дать 500 с текстом `Internal Server Error`. Общий обработчик доменных ошибок приложения имеет отдельную структуру `{error: строка}` и статус 400; его срабатывание на стенде не проверялось.

HTTP 200 подтверждает ответ обработчика о сохранении попытки, но не окончательность математической оценки. В частности, технический отказ оценивания сейчас может возвращаться как 200 с нулём и `needs_curator=true`; существование задачи куратора этим не подтверждается.

## Целевой интерфейс C-11

| Операция | Результат |
|---|---|
| `POST /api/v2/submit` | Синхронная отправка; 200 с окончательным или предварительным результатом |
| `GET /api/v2/tasks/{task_id}/attempts` | Собственные попытки, созданные по контракту 2.0 |

Новая версия маршрута нужна из-за несовместимого изменения полей ответа и правил входной валидации. Существующие маршруты сохраняются для прежних клиентов. Переход сайта на v2 выполняется после реализации сервера. Адрес `https://api.example.invalid` в спецификации — заполнитель, а не работающий сервис.

Вход: обязательные `task_id` и `text`; неизвестные поля отклоняются. Длина текста — 1–40 000 символов Unicode до преобразований, включая пробелы и переводы строк; требуется непробельный символ. Символ здесь означает кодовую точку Unicode, а не байт и не элемент UTF-16. Исходник сохраняется без обрезания и математического исправления. Представление для обработки хранится отдельно. Автор, условие, критерии и максимальный балл задаются сервером.

При успехе обязательны все поля соответствующей ветви схемы, включая поля со значением `null`. Время `created_at` содержит часовой пояс. Публичный ответ включает только сведения ученика, без внутренних ответов провайдера и служебной диагностики.

| Поле | Правило |
|---|---|
| `schema_version` | Строка `2.0` |
| `id`, `task_id` | ID сохранённой попытки и задачи |
| `solution_text` | Неизменённый исходный текст ученика |
| `result_status` | `final` — окончательный результат; `provisional` — предварительный |
| `score` | Единственное публичное поле балла; `null` допустим только для предварительного результата |
| `max_score` | Положительный максимум, зафиксированный для попытки |
| `is_solved` | Истина только при окончательном полном балле |
| `feedback` | Непустое общее пояснение и массив комментариев; балл здесь не дублируется |
| `decision.source` | Источник принятого балла либо `none`, когда оценка отсутствует |
| `decision.reason_codes` | Причины решения; для предварительного результата массив непустой |
| `review` | `null` для автоматического окончательного результата; объект с ID и статусом сохранённой ручной проверки в остальных случаях |

Источники решения: согласие оценщиков `primary_agreement`, отдельный оценщик `grader_a`/`grader_b`, арбитр `arbiter`, калибровка `calibration`, предметное правило `input_rule`, куратор `curator`, отсутствие оценки `none`. В этом контракте `input_rule` используется для нуля за отсутствие хода решения по BR-012.

Коды причин — расширяемые непустые строки; начальные примеры: `GRADER_UNAVAILABLE`, `INSUFFICIENT_EVIDENCE`, `CONFIRMED`. Неизвестный код не должен ломать отображение: клиент показывает `feedback.general_comment`. Добавление нового значения закрытого перечисления, нового поля при запрете неизвестных полей либо нового обязательного поля требует согласования новой версии контракта.

## Согласованность результата

1. Числовой балл находится в пределах `0 ≤ score ≤ max_score` и имеет источник, отличный от `none`.
2. При `final` балл обязателен; `is_solved` эквивалентен полному баллу. Автоматическое окончательное решение имеет `review=null`.
3. При `provisional` всегда `is_solved=false`, даже если предварительный балл равен максимуму. Обязательны причина и `review` со статусом `pending` либо `in_progress`.
4. После куратора результат становится `final`, источник — `curator`, `review.status=completed`; сохраняется ID той же ручной проверки.
5. Если доступной оценки нет, но есть пригодная исходная работа и подтверждённое основание ручного разбора, допустим предварительный ответ с `score=null` и сохранённой задачей куратора. Если продолжение не организовано, возвращается техническая ошибка.
6. HTTP 200 возвращается после фиксации попытки и связанной задачи куратора, если она требуется. Существование записи по `review.id` проверяется на уровне приложения и хранилища, а не JSON Schema.

Структурные ограничения находятся в OpenAPI. Сравнение разных полей, соответствие источника оценки и состояния ручной проверки дополнительно описаны в `x-invariants` и проверяемых моделях из [tools](../tools/README.md). Наличие этих моделей не означает реализацию v2 в приложении.

## Ошибки и повторная отправка

У целевой ошибки обязательны `schema_version`, диагностический `request_id`, `result=null` и объект `error` с `code`, безопасным `message` и `retryable`. ID запроса нужен для поиска служебной диагностики; это не ID попытки и не ключ идемпотентности.

| HTTP | `error.code` | Смысл и действие клиента |
|---|---|---|
| 401 | `AUTH_REQUIRED` | Повторно войти; оценивание не запускалось |
| 404 | `TASK_NOT_FOUND` | Обновить выбранную задачу; оценивание не запускалось |
| 422 | `VALIDATION_ERROR` | Исправить поля или длину текста; оценивание не запускалось |
| 429 | `RATE_LIMITED` | Дождаться срока из обязательного `Retry-After` в секундах, затем отправить осознанно |
| 503 | `GRADING_UNAVAILABLE` | Оценка не получена и передача на ручную проверку не подтверждена; `result=null` |
| 500 | `PERSISTENCE_FAILURE` | Подтверждён откат или отсутствие фиксации; после восстановления можно повторить |
| 503 | `PERSISTENCE_OUTCOME_UNKNOWN` | Фиксация не подтверждена; `retryable=false`, проверить историю |
| 500 | `INTERNAL_ERROR` | Для отправки исход неизвестен: `retryable=false`, проверить историю; чтение истории можно повторить |

`retryable=true` означает допустимость повторного действия после устранения причины, а не команду автоматического повтора POST. `Idempotency-Key` в синхронном API не поддерживается. При разрыве связи или неизвестном исходе клиент сохраняет введённый текст и предлагает посмотреть историю. Отсутствие результата в истории не доказывает остановку обработки; новая отправка может создать вторую попытку. Идемпотентность C-10 относится к отдельной интеграции LMS.

## История и данные

Целевая история возвращает только попытки v2 текущего ученика, в порядке `created_at DESC, id DESC`; правила `limit`/`offset` сохранены. При конкурентных вставках страницы могут сдвигаться. Миграция старых попыток в v2 в этот контракт не входит: старые записи доступны через прежний маршрут.

Ответ истории строится из сохранённого результата и текущего состояния ручной проверки. Поля связаны с сущностями `AttemptV2` и `AttemptReview` в [целевой ERD сайта](../diagrams/erd.md). Автоматический результат сохраняется отдельно от утверждённого куратором. API назначения и завершения ручной проверки требует отдельного сценария и не входит в эти две операции.

## Перед реализацией

Контракт определяет желаемое поведение. Общий числовой срок HTTP-обработки по NFR-PERF-01, эксплуатационная настройка ограничения частоты и сроки хранения данных требуют согласования. Эти параметры не выдаются за измеренные характеристики продукта. Выполненные проверки и оставшаяся приёмка перечислены в [протоколе](12_api_verification_protocol.md).

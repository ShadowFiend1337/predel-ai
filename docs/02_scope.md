# Границы проекта

## Предмет кейса

Системный анализ проверки развёрнутого математического решения: от приёма данных до сохранённой оценки, предварительного результата или контролируемой ошибки. Основной предметный охват — задания №13, №14 и №15 профильного ЕГЭ.

## Статусы описаний

| Пометка | Значение |
|---|---|
| Реализация | Поведение или структура подтверждены предоставленным кодом |
| Целевое требование | Нормативное поведение, которое должна обеспечивать система |
| Целевая модель | Спроектированное расширение, не являющееся действующим API или процессом |
| Требует согласования | Указаны вопрос, ответственный и способ принятия решения |

Статус «реализовано» не означает подтверждённое качество математической проверки. Наличие тестов также не означает выполнение всех требований. Подробное соответствие — в [матрице реализации](20_implementation_status.md).

## Реализованная граница

- Собственный сайт и аутентифицированный пользователь.
- Синхронные `POST /api/submit` и `POST /api/submit/photo`.
- История попыток `GET /api/tasks/{task_id}/attempts`.
- Текст, изображения и поддерживаемые файлы; PDF обрабатывается по текстовому слою.
- Для №13–15: разбор шагов, ограниченные программные проверки, оценки A/B, условный арбитр и калибровка.
- Для остальных вариантов: прежняя проверка с текстовыми маркерами.
- Сохранение попытки и промежуточных результатов в БД.

Клиент передаёт идентификатор задачи каталога и решение. Условие, эталон, вариант промпта и максимальный балл определяет сервер. Отдельное поле номера задания клиент текущего API не передаёт.

## Целевое поведение основного сценария

1. Система проверяет входные данные до платных вызовов ИИ.
2. Исходная запись сохраняется; техническая нормализация не исправляет математику ученика.
3. Каждый результат компонента проходит проверку структуры и ссылочной целостности.
4. Решение об оценке учитывает доступность данных, правила оценивания и необходимость ручной проверки.
5. Техническая ошибка не превращается в нулевой математический балл.
6. Пользователь получает сохранённый результат и понятный следующий шаг.

Эти требования задают желаемое качество продукта. Отличия текущей реализации вынесены в отдельную техническую матрицу, чтобы не перегружать основной сценарий.

## Целевой API сайта

Сценарий отправки текста формализован в C-11: `/api/v2/submit` и собственная история v2. Контракт включает окончательность, технические ошибки без балла и ссылку на связанную задачу куратора. Текущие маршруты сохраняются отдельно. [Спецификация и границы проверки](11_api_specification.md).

## Целевая интеграция с LMS

В первую проектируемую версию входят создание `CheckJob`, получение состояния и результата через polling, идемпотентность и изоляция данных клиентов. Решение передаётся текстом, `task_id` ссылается на согласованный каталог PredelAI. Загрузка файлов внешней LMS — следующий этап после определения механизма передачи и доступа.

Webhook описывается как дополнительный вариант доставки. При его добавлении необходимы отдельные правила аутентификации, повторной доставки и дедупликации событий.

## Целевая ручная проверка

Куратор получает задачу в очереди, просматривает исходное решение и основания автоматической оценки, подтверждает или изменяет результат. Система сохраняет автора, время, причину изменения и исходную автоматическую оценку. На одну проверку в первой версии приходится не более одной записи ручной проверки.

Нельзя сообщать, что задача передана куратору, пока она не сохранена в очереди. Операционный процесс куратора относится к целевой модели.

## За границами первой целевой версии

- Универсальный математический решатель для всех типов задач.
- Автоматическое расширение на остальные задания ЕГЭ.
- Вычисляемая вероятность правильности всего результата без методики калибровки.
- Отмена работающей проверки и повторное открытие завершённой проверки.
- Несколько последовательных ручных ревью одной проверки.
- Обязательная доставка webhook и загрузка файлов через внешний LMS API.

## Управление изменениями

Расширение охвата требует критериев оценивания, тестовых примеров, требований, ответственного и процедуры приёмки. Числовой результат публикуется с источником и методом расчёта. Исходные ученические работы и закрытый датасет не включаются в репозиторий.
